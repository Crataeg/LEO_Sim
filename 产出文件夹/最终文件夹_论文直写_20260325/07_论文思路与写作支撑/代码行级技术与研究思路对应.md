# 代码行级技术与研究思路对应

## 1. 这份文档的用途

这份文档不是重复代码行级报告，而是回答一个更适合写论文的问题：

`每一类代码技术，在论文里应该对应成什么研究思路和写作角色？`

## 3. 最适合进正文的方法主线

如果正文只保留最强的一条主线，建议是：

1. 场景建模
2. 链路预算
3. 干扰耦合
4. 路由与 E2E
5. 最劣场景搜索
6. 开源星座数据锚定

### 对应代码

- `LEO_StarNet_EMC_V7_0_Engineering.m`
- `emcPrecomputeLinkPower.m`
- `emcBuildLinkModel.m`
- `simulateStarNetV7.m`
- `emcCombineE2E.m`
- `trainOrLoadJammerGAN.m`
- `worstCaseObjectiveV7.m`

## 4. 更适合放到补充材料的部分

### 推荐放补充材料

- Dashboard 实时联动
- STFT 识别模块细节
- 旧 Simulink 原型链
- 导出脚本与 UI 逻辑

### 原因

- 它们确实有价值
- 但会稀释正文主线
- 容易让审稿人觉得文章过于“平台介绍”

## 5. 当前代码问题在论文中怎么说最稳

### 可以直接说的

- 平台采用系统级功率评估方法
- 上下行链路和端到端指标被统一到同一时变框架中
- 干扰识别模块作为辅助解释链路接入

### 必须收住的

- 不能把上行代理模型说成严格物理建模
- 不能把 STFT 识别器说成已经完成高可信标注训练
- 不能把 InfoGAN 包络生成说成实测干扰学习

## 6. 最终建议

这份代码基础最适合支撑一篇：

`以系统级评估和真实公开星座数据为主轴、以最劣搜索为增强、以识别模块为补充解释的卫星通信论文。`
