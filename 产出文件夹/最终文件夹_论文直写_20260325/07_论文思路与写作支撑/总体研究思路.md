# 总体研究思路

## 1. 论文主线应该怎么收

当前最合理的主线不是把所有模块都并列展开，而是收成下面这一句：

`面向真实公开星座数据约束下的车载低轨卫星通信系统链路/EMC评估框架。`

然后把其他模块按层次放进去：

- 主链：
  - 星座建模
  - 链路预算
  - EMC 干扰注入
  - DL/UL/E2E 指标
- 增强链：
  - 最劣工况搜索
- 辅助链：
  - STFT 干扰识别

## 2. 文章结构建议

### Section 1: Introduction

- 讲车载 LEO 通信的意义
- 讲频谱共存与 EMC 风险
- 讲现有研究为什么不够
- 引出本文的统一框架

### Section 2: Related Work

- LEO/NGSO 场景与系统级仿真
- EMC / 干扰共存
- 最劣搜索
- 干扰识别

### Section 3: System Model and Platform Architecture

- 星座和地面站
- DL/UL/E2E
- ISL 路由
- jammer 注入
- 合规判据

### Section 4: Data-Informed Constellation Modeling

- 为什么要引入 `Starlink / Qianfan / GeeSat`
- 开源数据源是什么
- 如何从公开数据得到星座壳层和可视化图

### Section 5: Worst-Case EMC Evaluation

- baseline vs worst-case
- 干扰功率分解
- 最劣包络与失效窗口

### Section 6: Interference Identification as an Auxiliary Module

- 不把它当主创新
- 强调它是解释模块
- 说明旧问题和模块级改进思路

### Section 7: Discussion

- 平台优点
- 工程代理点
- 局限
- 后续工作

## 3. 当前最适合拿来写结果的东西

### 已经可以直接写的结果

- `Starlink / OneWeb / Qianfan / GeeSat` 的开源数据对比
- 当前平台的 `DL / UL / E2E` 指标
- 最劣工况下的吞吐下降和中断窗口
- 关键帧识别问题与改进逻辑

### 暂时不要写得太满的结果

- 不要把 STFT 模块写成“高精度识别器”
- 不要把 InfoGAN 写成“已经有实测支撑的干扰生成器”
- 不要把当前 `12 张关键帧` 准确率直接当成模型能力结论

## 4. 论文口径怎么稳住

### 应该强调

- 统一平台
- 系统级评估
- 数据锚定
- 工程可复现
- 最劣场景

### 应该降调

- Dashboard
- 识别模块绝对准确率
- 过强的 AI 表述

## 5. 当前最值得推进的一步

如果只做一件事，最值得推进的是：

`在模块改进版代码副本上，把真实公开星座数据转换成 external constellation .mat，并用它驱动一条新的场景分支。`

这样会直接把文章从：
- “项目平台介绍”

推到：
- “数据驱动的车载 LEO 链路/EMC 评估论文”
